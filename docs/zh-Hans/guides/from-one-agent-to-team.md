每一个 Monad 部署本身就已经是一个 mesh —— Monad Mesh 就是 Agent 团队运行时，单个 Agent 只是成员数为一的 mesh。组建团队是在同一个运行时里增加成员和结构，从来不需要迁移到另一个运行时。

从能产出有效工作的最小 mesh 开始。只有当工作真的产生了协调需求时，才增加团队结构。

## 阶段 1：一个受监督的 Agent

用默认成员创建一个会话，由 Monad Agent Runtime 承载。把审批范围收窄，逐个检查工具调用，确定合适的模型、技能、工具和沙箱根目录。目标是一个可靠的单工人循环，不是最大化自治。

## 阶段 2：把持久工作放进项目

当多个会话应当共享同一个工作区根目录和稳定的协作环境时，创建项目。项目持有配置和成员身份；每一次对话仍然是它自己的持久项目会话。

用不同的会话承载彼此独立的工作线程。想在继承历史的前提下尝试另一条路时，给会话开分支；只有当你确实想重写原线程时，才使用恢复。

## 阶段 3：加入一个专职成员

当出现了不同的能力、Agent 运行时或职责时，才加入第二个成员。成员可以由第一方运行时承载，也可以由第三方 Agent、ACP Agent 或对等守护进程承载——见[选择运行时](/zh-Hans/guides/choosing-runtime)。给它明确的角色和有边界的能力集合。不要加入多个可互换的 Agent：没有明确职责划分的参与者只会抬高路由和复核成本。

## 阶段 4：委派与观察

委派边界清晰、预期产出明确的工作。把决定、阻塞、审批和产物都挂在项目会话上。观察要能回答四个问题：谁在做、改了什么、卡在哪、什么需要人来决定。

## 阶段 5：有意识地放大自治

只有当反复出现的证据表明能力、沙箱和产出复核都是安全的，才扩大审批范围。在每个阶段都保留中断路径、预算上限、持久审计历史和恢复行为。

结果仍然是同一个 mesh。单 Agent 部署和多 Agent 项目的区别在于成员名册和协调方式，而不在于事实来源。
