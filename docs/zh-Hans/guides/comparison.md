这个领域里的多数工具**协调的是住在别处的 Agent**。Agent 的身份、记忆、权限和历史，属于真正在运行它的那个产品——某家厂商的 CLI、某个托管服务、某个聊天客户端——协调层只是从外面指挥这些进程。外层工具消失时，什么持久的东西都不会留下；内层产品变化时，团队也跟着变。

**Monad 就是 Agent 住的地方。** 本地的 `monad` 守护进程自己持有身份、能力、权限、记忆、会话、协作状态、审批和审计历史。Monad Mesh——Agent 团队运行时——就是这份所有权的运转形态。其他运行时通过第三方 Agent 适配器、Agent Client Protocol 和对等联邦作为成员加入。用不是自己写的运行时托起一支团队，只有先拥有状态的那一层才做得到。

## 这带来什么改变

**工作比任何客户端和任何厂商活得更久。** 在 CLI 里开始的会话，可以在浏览器、终端界面、编辑器或聊天渠道里继续。更换承载某个成员的运行时，不会产生新的队友或新的孤岛——成员身份、它的历史和绑定关系都留在原处。

**一个守护进程，不是一套要部署的平台。** Monad 安装为单个二进制，作为一个绑定回环地址的长期进程运行。在第一个 Agent 跑起来之前，不需要先架设集群、消息服务器、网关或对象存储；`curl | bash`，然后 `monad`。它是为你已经在用的那台机器准备的运行时。

**治理在 Agent 之下，而不是在它旁边。** 对于由 Monad Agent Runtime 执行的工作，审批在工具调用运行之前就挡住它，并且在无人应答时失败关闭。工具参数经过 schema 校验，文件系统路径针对沙箱根目录解析，出站请求经过 SSRF 过滤。子进程运行在操作系统自身的约束之下——macOS 用 Seatbelt，Linux 用 bwrap 或 Landlock 加 seccomp，Windows 用 AppContainer——网络出站通过本地代理过滤。由第三方运行时承载的成员在该运行时自己的进程和权限模型内执行，所以 Monad 通过观察和代理它的审批提示来治理它，而不是把它装进沙箱。对两者而言，审计都是一等对象，不是一行日志。

**默认中立、默认本地。** 不需要账号，不做许可证校验，不发遥测，不锁定厂商：你的状态存放在 `~/.monad` 下，模型服务商由你选择，代码以 MIT 许可证发布。唯一离开这台机器的流量，是你自己配置的流量。

## 什么时候它不是合适的工具

如果你只想要一次用完即弃的问答，独立的聊天客户端更简单。如果某一家厂商的工作流已经覆盖了整个任务，那家厂商的 CLI 单独用就够了——等你之后想让它被监督、变持久、成为团队的一部分时，Monad 会把它作为 mesh 成员运行，而不是替换它。

当工作必须比某个界面活得更久、需要在客户端之间流转、涉及不止一个 Agent 运行时，或者必须待在同一套策略与审计边界之内时，Monad 才值得它的位置。

## 一句话版本

| 关注点 | 住在客户端或厂商进程里的 Agent | Monad |
|---|---|---|
| 谁拥有身份和记忆 | 运行该 Agent 的产品 | 本地守护进程 |
| 持久性 | 绑在那个产品的会话上 | 会话、成员、产物和审计跨重启保留 |
| 客户端选择 | 通常只有一个界面、一个孤岛 | Web、CLI、TUI、编辑器、API 和聊天渠道驱动同一份状态 |
| 执行 | 一个运行时 | 任何运行时都可作为 mesh 成员：第一方、第三方、ACP 或对等守护进程 |
| 治理 | 产品各自的提示 | 第一方执行有审批门、沙箱和出站控制；每个成员都有观察、代理审批和审计 |
| 部署 | 安装一个产品，或部署一套平台 | 一个本地守护进程 |
